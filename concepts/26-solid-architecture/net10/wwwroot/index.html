Conceito 26: Princípios SOLID e Arquitetura Limpa

Separação estrita em camadas (Domain, Application, Infrastructure, Presentation) e Inversão de Dependências no .NET 10

.NET 10 (Kestrel - Porta 7600)

Execução de Caso de Uso (CadastrarClienteUseCase)

O controller não sabe como o cliente é salvo nem como é notificado. Ele delega o comando para o caso de uso, que orquestra a entidade de domínio e as interfaces de infraestrutura.

Camadas da Arquitetura Limpa

1. Presentation (Controllers / Minimal APIs)
Recebe HTTP DTO, invoca o Use Case e responde com status 201 Created ou 400 Bad Request. Zero regra de banco ou negócio.
2. Application (Use Cases & Interfaces)
CadastrarClienteUseCase, IClienteRepository, INotificadorService. Orquestra o fluxo sem conhecer detalhes técnicos de persistência.
3. Domain (Entidades & Regras Invariantes)
Classe Cliente. Valida regras fundamentais (email válido, nome obrigatório, crédito não negativo). Zero dependências externas.
4. Infrastructure (Repositórios & Mensageria)
ClienteRepositoryEmMemoria, NotificadorConsoleService. Implementa os contratos definidos na camada de aplicação.

Quadro Comparativo: .NET Framework 4.8.1 vs .NET 10

Princípio / Característica .NET Framework 4.8.1 (Legado) .NET 10 (Moderno)
Single Responsibility (SRP) God Controllers: misturam lógica de view, validação, SQL direto e envio de email na mesma action. Cada Use Case executa exatamente uma operação de negócio bem delimitada.
Dependency Inversion (DIP) Instanciação direta de novas classes concretas (new ApplicationDbContext(), new SmtpClient()). Toda dependência é baseada em interfaces resolvidas pelo container de DI nativo.
Inversão de Controle Service Locator (DependencyResolver.Current.GetService) ou frameworks manuais de terceiros. Injeção de dependências embutida no runtime com ciclos de vida Transient, Scoped e Singleton.
Isolamento do Domínio Entidades dependentes de atributos de validação do ASP.NET e System.Web. Entidades de domínio puras com validações invariantes em métodos de negócio.
